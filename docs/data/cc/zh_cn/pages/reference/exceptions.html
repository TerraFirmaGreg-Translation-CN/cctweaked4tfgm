CraftOS的异常协议

默认情况下，Lua 表示错误是纯字符串。文件名和行号可能会附加到错误消息（例如 example.lua:12: error message），但所有其他信息（例如堆栈跟踪）都会丢失。

为了在支持捕获错误（pcall、coroutine.resume）的 API 中保留此信息，CraftOS 支持更丰富的错误形式，捕获它们被抛出的上下文，称为“异常”。这些异常可以由协程管理器（例如 parallel 创建，以跨协程边界保留错误信息，从而允许 shell 和 Lua REPL 显示错误的精确来源和位置。

异常定义为具有以下内容的表：

  • 一个 message 字段，类型为 string。
  • thread 字段，类型为 thread。
  • 元表，带有 __name = "exception" 字段。

例子

作为一个例子，让我们考虑最简单的协程管理器，它只是生成一个新的协程并将事件转发给它。当我们在协程内部出错时，请注意 shell 不会显示丰富的错误，因为堆栈跟踪信息丢失了！

local function run(fn, ...)
  local co = coroutine.create(fn)
  local ok, result = coroutine.resume(co, ...)
  while coroutine.status(co) ~= "dead" do
    local event = table.pack(os.pullEventRaw())
    if result == nil or filter == "terminated" or event[1] == filter then
      ok, result = table.pack(coroutine.resume(co, table.unpack(event, 1, event.n)))
    end
  end

  if not ok then error(result, 0) end
end

return run
local run = require "run"
run(function()
  error("ohno")
end)

我们可以通过更新协程管理器以在发生错误时抛出异常来解决此问题。 shell 现在在退出时打印丰富的错误。

-- NEW: Define our exception metatable.
local exception_mt = {
  __name = "exception",
  __tostring = function(self) return self.message end
}

local function run(fn, ...)
  local co = coroutine.create(fn)
  local ok, result = coroutine.resume(co, ...)
  while coroutine.status(co) ~= "dead" do
    local event = table.pack(os.pullEventRaw())
    if result == nil or filter == "terminated" or event[1] == filter then
      ok, result = table.pack(coroutine.resume(co, table.unpack(event, 1, event.n)))
    end
  end

  if not ok then
    -- NEW: If we have a string error, wrap that into an exception instead
    if type(result) == "string" then
      error(setmetatable({ message = result, thread = co }, exception_mt))
    else
      error(result, 0)
    end
  end
end

return run
local run = require "run"
run(function()
  error("ohno")
end)

parallel 和例外情况

使用上述模式时可能遇到的一个问题是，异常不会由 parallel 函数抛出。例如，下面这个程序与之前有同样的问题，并且不会打印详细的错误信息。

local run = require "run"
run(function()
  parallel.waitForAny(function()
    error("ohno")
  end)
end)

默认情况下这样做是为了保持 CraftOS 的向后兼容性。某些用户代码捕获从 parallel 函数中抛出的错误，并检查错误，并尝试将这些错误转换为异常将破坏该代码。但是，如果您运行此代码 without 我们的 run 函数，您会注意到显示了丰富的错误：

parallel.waitForAny(function()
  error("ohno")
end)

在内部，parallel 函数尝试确定用户代码是否捕获错误消息（使用 pcall/xpcall 或 coroutine.resume。如果从未观察到错误，则可以安全地将其包装到异常中！

我们在这里看到的是 parallel 对我们的协程管理器一无所知，因此假设抛出异常是不安全的。

这可以通过将子协程中的第一个函数设置为神奇的 debug.getregistry().try_barrier 函数来解决。这个功能：

  • 接受“上下文”、要调用的函数以及函数的参数作为参数，然后立即调用该函数。
  • “上下文”是一个包含以下内容的表：
    • 一个 co 字段，包含父协程。
    • 可选的 can_wrap 字段，指示是否可以包装异常。

我们的协程管理器对此的支持如下所示：

-- NEW: Define our magic try_barrier function:
local try_barrier = debug.getregistry().cc_try_barrier
if not try_barrier then
    local function bounce(...) return ... end
    try_barrier = function(parent, f, ...) return bounce(f(...)) end
    debug.getregistry().cc_try_barrier = try_barrier
end

local exception_mt = {
  __name = "exception",
  __tostring = function(self) return self.message end
}

local function run(fn, ...)
  -- NEW: Start our coroutine using the try_barrier function instead. We use
  -- { can_wrap = true } to tell parallel that it can always wrap errors into
  -- exceptions.
  local co = coroutine.create(try_barrier)
  local ok, result = coroutine.resume(co, { co = co, can_wrap = true }, fn, ...)

  while coroutine.status(co) ~= "dead" do
    local event = table.pack(os.pullEventRaw())
    if result == nil or filter == "terminated" or event[1] == filter then
      ok, result = table.pack(coroutine.resume(co, table.unpack(event, 1, event.n)))
    end
  end

  if not ok then
    if type(result) == "string" then
      error(setmetatable({ message = result, thread = co }, exception_mt))
    else
      error(result, 0)
    end
  end
end

return run
local run = require "run"
run(function()
  parallel.waitForAny(function()
    error("ohno")
  end)
end)
